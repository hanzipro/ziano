## 一、已拍板的決策

1. **suffix 改寫語意**：`-dan`／`-yue` 表「傳承強度」，`-tc` 從此**只**表地區版
   （只剩霞鶩用）。解掉 TODO #6「`-tc` 在兩家指相反方向」的矛盾。
2. **`font-family` CSS 名一起改**（使用者基數還小，趁早）。
3. **度量統一目標值 `(A−D)/2 = 0.380em`**（＝字身框中心，也是 Hiragino／YuMincho
   ／源起／芫荽的現值 → 連 webfont 失效退到系統字都不跳）。
4. **ziano 走 CSS 層**（`cssgen.py` 輸出 descriptor），**DTJ 走字體層**（build 時
   改寫 `hhea` ＋ `usWin*`）。理由見 `../vertical-baseline-offset.md` §「改在字體裡
   還是改在 CSS」——ziano 的產品就是 CSS 包，且 CSS override 能一次蓋掉
   `hhea`／`usWin*` 的平台分歧；DTJ 則額外賺到行框不再被標點撐大。
5. **源樣 GenYo 不改名**：維持 0.1.x 收尾，`npm deprecate` 指向源起。
6. **不做 legacy family alias**：han.css v4 尚未發布，是新名唯一的下游消費者
   ——直接改 han 就好，當舊名沒存在過。少一組 `@font-face`、少一個「同頁混用
   兩個名字會重複下載」的陷阱，也讓「沒有後綴」不再暗示任何取捨（8 個 cut 全部
   帶 `-dan`／`-yue`）。
7. **rc 先行**：兩邊都先發 `0.2.0-rc.0`（`--tag rc`）放幾天，確認無事再推
   `latest`。舊包名的 `npm deprecate` 等 stable 才做——rc 期間 deprecate 會把人
   推去裝 rc。

### 2.1 改名（roster ＋ cssgen ＋ README ＋ demo）

**原則**：兩個 cut **都**帶後綴，不留無後綴的 base——「沒有後綴」從此不再暗示

| `shanggu-sans` | `shanggu-sans` | `Shanggu Sans` | 丹 |
| `shanggu-serif-tc` | `shanggu-serif-yue` | `Shanggu Serif Yue` | 月 |
| `shanggu-sans-tc` | `shanggu-sans-yue` | `Shanggu Sans Yue` | 月 |
| `genki-min` | `genki-serif-yue` | `Genki Serif Yue` | 月 |
| `genki-gothic` | `genki-sans-yue` | `Genki Sans Yue` | 月 |
| `genki-min-tc` | `genki-serif` | `Genki Serif` | 丹 |
| `genki-gothic-tc` | `genki-sans` | `Genki Sans` | 丹 |
| `genyo-*`（4） | 不動 | 不動 | 收尾 deprecate |

- **Min／Gothic → Serif／Sans**：理由不是「日文不好」，而是 **roster 內部一致性**
  ——旗艦尚古早就叫 `Shanggu Serif`／`Sans`，同一份清單裡並存兩套命名法比任一套
  都糟。而且 Serif／Sans 有最強的 CJK 前例：思源宋體／黑體的官方拉丁名就是
  **Source Han Serif／Sans**（Noto CJK 同理），尚古與源起都是思源後裔，跟著叫是
  回到血緣正名，不是硬套西文分類；也正好對上 `usage.md` 教人接的
  `--font-serif`／`--font-sans-serif` generic。
  📌 但要在 README 留一行對照「＝上游 GenKi Min／GenKi Gothic」——Min／Gothic 不是
  上游寫錯，是 ButTaiwan 的系列慣例（源流 GenRyuMin、源雲 GenWanMin、源樣
  GenYoGothic），承自 Source Han 的日文血統；沒有對照表使用者會查不到原字。
  中文名不動（源起明體／源起黑體），源樣 GenYo 收尾包不跟進。
- **唯一的下游是 han.css v4，而它還沒發**——所以不留 legacy alias，直接改 han
  （checklist D 組）。少一組 `@font-face`、CSS 不會加倍，也沒有「同頁混用新舊名
  被當成兩個 family、同一 slice 下載兩次」這個陷阱。
- 新 family 名離上游保留名更遠，**RFN gate 只會更寬鬆**；但仍要重跑一次 gate 並
  更新各包 `LICENSE` 的 name-table 說明。
- 8 個舊包名：**stable 發布之後**才 `npm deprecate` 指向新名（rc 期間 deprecate
  會把人推去裝 rc）。不補發 `0.1.1`。
- 結果：**breaking 有兩項**——8 個包改名＋`font-family` 改名（一起發生，一次遷移），
  以及 `line-height: normal`。

### 2.2 度量統一（cssgen）

每條 `@font-face` 追加：

```css
ascent-override: 110%;
descent-override: 34%;
line-gap-override: 0%;
```

差 `0.76em` 決定直排位置（本次要修的），和 `1.44em` 決定 `line-height: normal`
——取 1.44 是為了貼近尚古現值，讓沒設 `line-height` 的頁面不會突然縮排。全 16 個
family 一律套同一組，包含不改名的霞鶩／芫荽／Klee。

實測（Chromium 直排、`font-size: 100px`、理想中心 152）：尚古原樣 163.0 →
override 後 158.0，霞鶩 156.5，殘差 ≤0.015em（原本 0.0965em）。

### 與 `emphasis-font.md` 的交互點

那份計畫（U+25CF 拆成獨立的 `Diantenjeom Emphasis`）和本批次同一個 pipeline，
合併做，但有三個**必須一起想**的接點：

1. **它是本批次「DTJ 走字體層」的鐵證**。`emphasis-font.md` 已實測：`@font-face`
   的 `ascent-override`／`descent-override` **對著重號無效**——Chrome 繞過覆寫直讀
   原始度量表（同一支字當主字體時 override 生效，證明不是寫錯）。所以 DTJ 這邊
   只有改檔案這條路，和 §一·4 的決策一致。
2. ✅ **兩個目標值其實是同一個數，沒有取捨**（2026-08-01 實測，原本擔心會打架）。
   outset ＝`(asc+|desc|)/upem × 0.5em`，中央基線偏移 ＝`(asc−desc)/2`；只要
   `descent ≤ 0`（正常字體都是），這兩式恆等——**根本無法分開調**。而且也不必：
   著重號不是排在正文的中央基線上，是排在一條寬度就等於 outset 的側欄裡。
   實測 60px 直排 `text-emphasis: filled sesame`，hhea 從 `600/0` 換成 `680/+80`
   （outset 0.30→0.38em、中央基線值不變）標記只外移 5px＝0.083em，正好是 outset
   差，沒有第二項。結論：Emphasis 維持 `hhea 600/0`，照 `emphasis-font.md` 原案。
3. **DTJ 本體的度量正規化不影響 Emphasis**：兩支是不同檔案，A1 和 A3 各改各的。

### 8.7 著重號位置：三家的預設值不一樣（2026-08-02，真 Safari 實測）

`lang="zh-Hant"`、未指定 `text-emphasis-position` 時的 computed value：

| | 橫排 |
|---|---|
| Chromium | `over`（標在字**上**方） |
| Firefox | **`under`** |
| Safari | **`under`** |

CSS 規範的 initial value 是 `over right`，但註明 UA *should* 對中文用 `under right`
——**Firefox 與 Safari 照做了，Chromium 沒有**。而 `under` 才是教育部《重訂標點符號
手冊》的橫式慣例（著重號標在字的下方；直式標在右方）。

後果：同一頁在 Chromium 標在字上、在另外兩家標在字下，看起來就像「Safari 沒畫」。

**所以位置必須寫死**，而且直排要分開給值——直排時 `over` 指的是欄的**右側**，正是
著重號該在的位置：

```css
em { text-emphasis-position: under right; }          /* 橫排中文 */
.vertical em { text-emphasis-position: over right; } /* 直排中文 */
```

demo 已照此固定並加了位置切換；三家 computed 現在都是 橫 `under` ／直 `over`。
**這條該進 han.css**：它比 ziano／DTJ 更該替使用者處理這個預設值差異。

### 8.12 決定不做：han 的 `--han-font-emphasis`

`Diantenjeom Emphasis` 掛到 `<em>` 前面。**做不到，也不該做**：

- 反向做法（把標記字體塞進四條 composite 的最前面）更糟：該字體刻意不帶

  標點層已經在管。

### 9.1 名字的後果

**查過了：沒有任何一個包換了上游來源。** 逐一比對 `v0.1.0:roster.toml` 與現行
roster 的 `member`／`asset`，每個存活下來的 id 都指著同一個檔案。改名是純改名。

| 類別 | 包 | 後果 |
|---|---|---|
| **同名、同源** | `shanggu-serif`、`shanggu-sans`、`genyo-*`×4、`lxgw-wenkai(-tc)`、`iansui`、`klee-one` | 字沒換，但檔案變了：度量 `1100/−340`、`：；` 補 vert、name 表加 `Ziano` 前綴；兩個尚古另多一套 `dan/` 樣式表 |
| **退役** | `shanggu-serif-tc`、`shanggu-sans-tc`、`genki-min`、`genki-gothic`、`genki-min-tc`、`genki-gothic-tc` | 永不再發版，得下 `npm deprecate` 指路 |
| **全新** | `shanggu-*-yue`×2、`genki-serif`、`genki-sans`、`genki-serif-yue`、`genki-sans-yue` | 首發。**撤除的話整個包會被鎖 24 小時**（§9.6） |

順帶對出來的事：**兩家的後綴本來就指相反方向**，也就是這輪要解掉的那個矛盾。

| 0.1.0 | 上游 | 刻 | → 0.2.0 |
|---|---|---|---|
| `shanggu-serif` | `ShangguSerif-VF` | 丹 | `shanggu-serif`（不動） |
| `shanggu-serif-tc` | `ShangguSerifTC-VF` | 月 | `shanggu-serif-yue` |
| `genki-min` | `GenKiMin2**TW**` | 月 | `genki-serif-yue` |
| `genki-min-tc` | `GenKiMin2**TC**` | 丹 | `genki-serif` |

尚古是「不帶後綴＝丹」，源起是「`-tc`＝丹」。因為 genki 四個名字全數退役、四個新名字
全是首發，沒有任何人的 `npm install` 會靜默換掉字——手動遷移的人才需要這張對照表。
